# Handler inventory (plan step H1)

Every HTTP route the VELA server serves, and how much of its path from request
to reply is formally covered. Read-only analysis: no code, proofs or checks
were changed.

Route table: `serverVELA/vela-server/src/routes.rs` (63 `.route(` calls at
lines 63-225, 64 method+path pairs: `/vault/schema` is one call with GET+POST). There is no other router: `lib.rs` has none, `main.rs` only wraps
`routes::build` with `RequestBodyLimitLayer(config.max_body_bytes, default
2 MiB)` and `TimeoutLayer(120 s)` (main.rs:267-276). When `WEB_DIR` is set,
`routes.rs:232-240` adds a static SPA `fallback_service`; it is not an API
route and is not counted.

## How to read a row

- **Auth & middleware** — the extractor(s) and any pre-driver limiter. Every
  route also gets the global layers listed below. `AuthSession` verifies the
  PASETO, expiry and hard cap, the JTI/device markers, the durable device row,
  the 300 req/min per-JTI limiter, and may renew the token
  (`middleware.rs:78-241`); `DeviceSession` additionally refuses a temporary
  web-session token (`middleware.rs:300-323`).
- **Request validation** — extractor types and the hand-written checks, with
  file:line. Unless the row says otherwise this code is **not** covered by any
  proof; the driver receives its results as observations.
- **Decision** — the extracted driver and the proved interpreter macro the
  handler expands (`security/formal/tests/test_handler_interpreters.py` pins
  each handler to its macro and forbids direct driver calls), with the turn
  budget and the proof-log README. `none` means no decision driver runs.
- **I/O** — the executor/pass objects and extracted plans. The `F-1` wave-1
  and wave-2 store-model proofs cover these per 08-formalization-status.md
  ("Executor honesty" and "Handler I/O outside ..."); the per-area evidence is
  in `proof-logs/current/{session,enrollment,share,send,recovery,vault}-executors`.
- **Reply** — how status and body derive from the verdict, and the `AppError`
  mapping (`error.rs:46-77`: `Internal` is scrubbed to a generic 500).
- **Bounded conformance** — tests that drive the route (or, where marked,
  only the driver/policy) against a real router or store.

Verdicts (exactly one per route):

- **driver+interpreter+executors proved** — the handler reaches a policy driver only through that crate's proved interpreter macro (or an equivalent proved loop), and every SQL/store operation in the request is an extracted plan proved against the store model.
- **partially proved** — at least the store statements are extracted plans with a store-model proof, but at least one part named in the row is ordinary handler code (usually: no decision driver at all, or a write whose authority is an inline branch).
- **no proof (read-only)** — no driver and no proved statement I/O; the route only reads (or probes) and its reply cannot change security state.
- **no proof (writes)** — a route that writes with neither a proved decision loop nor proved statement I/O.

## Summary

| Verdict | Routes |
|---|---|
| driver+interpreter+executors proved | 47 |
| partially proved | 15 |
| no proof (read-only) | 2 |
| no proof (writes) | 0 |
| **Total** | **64** |

The 15 partial routes split into 9 read-only request paths whose
store reads are proved plans but which run no decision driver (`GET
/device/enrollment-grant/:id`, `/devices`, `GET /vault/schema`, `/share/
inbox`, `/share/linked`, `/share/recipient/:user_id/ek`, `/sends`,
`/web-sessions`, `/web-session/:id/keys`) and **6 write-capable GETs** whose
authority is inline handler code: `/device/capsule` (read-once clear),
`/vault/epoch`, `/vault/sync`, `/vault/events`, `/vault/oram/...` (all four
reach `maybe_rollback` through `read_epoch`) and `/web-session/:id` (one-shot
clear). On the driver routes too, `read_epoch`/`resolve_write_epoch` may roll
back inside an executor method whose emitted effect is a read (finding 1).

No route is in **no proof (writes)**: every writing route's SQL/store statements are at
least extracted, rendered and proved as plans. The uncovered part of a write
is its decision loop, not its statements. Request parsing and reply rendering
are outside every driver proof (08, "Handler-to-driver interpreters": "Still
outside: request parsing and rate limits before a driver begins, response
rendering after its verdict").

## Findings

### 1. Writes whose decision is not a driver decision

All of these writes use proved plan statements; the gap is the **authority
decision**, which no interpreter theorem names.

**The lazy timeout rollback is reachable from every vault read.** `read_epoch`
(`vault/rekey.rs:369-372`) and `resolve_write_epoch` (`rekey.rs:285-300`) both
call `maybe_rollback` (`rekey.rs:137-182`). For an expired `FREEZING`
rotation that function applies `plan_timeout` and then runs `rollback_rekey`
(`rekey.rs:212`: begin, rollback CAS, shadow cleanup, commit). So:

- `GET /vault/epoch` and `GET /vault/sync`, `GET /vault/events` and
  `GET /vault/oram/...` perform this write straight from handler code;
- `GET /vault/chunk/:id` reaches it inside `GetChunkIo::read_epoch`
  (`chunk.rs:47-48`), and the chunk PUT/DELETE and ORAM PUT reach it inside
  their epoch resolution, i.e. **inside an executor method whose emitted
  effect is a read/resolve**. The interpreter proofs say the loop calls that
  method; they do not say the method may commit a rollback transaction. The
  statements are individually proved, but the "one call per emitted effect"
  claim does not describe this I/O.

**Two capsule deliveries are inline write decisions.**
`GET /device/capsule` (`device/capsule.rs:24`) conditionally clears an
enrollment capsule (`plan_clear_enrollment_capsule`, lines 84-99), and
`GET /web-session/:id` (`web_session/mod.rs:443`) clears the capsule to decide
one-shot delivery (`plan_capsule_clear`, lines 511-538). The status/expiry/
clear branches are handler code.

Suggested follow-up: give the capsule-delivery and poll paths drivers with
interpreter loops, and either route `maybe_rollback` through the abort
driver's loop (so the rollback is an emitted effect) or record the lazy
timeout as an accepted decision point with its own invariants and a rule that
its multi-statement I/O is invisible to the emitted-effect theorem.

### 2. The authentication extractor runs SQL outside every plan

`middleware.rs:114-188` performs two raw queries on every authenticated
request:

- `SELECT key_epoch FROM users WHERE id = ?` (line 137);
- `SELECT id FROM devices WHERE id = ? AND user_id = ? AND revoked = 0`
  (line 173).

The *decision* over their results is the proved pure `plan_admission`
(`middleware.rs:54`), and 08 exempts `plan_admission` as "a single pure
decision with no effect loop". The **reads themselves** are not extracted
plans and appear in no executor log. This applies to the 45 routes that
extract `AuthSession`/`DeviceSession`. A rewired or drifted query (wrong
column, wrong predicate, missing index-level guard) would not be caught by any
proof, only by review and the route-level tests. Suggested follow-up: move
both reads into `vela-session-policy::store` plans and extend the
session-executors model.

### 3. Parse and validation code that carries security weight

None of these is proved; each feeds a proved driver as a fact, so a parse bug
silently changes the driver's inputs.

- **`signed_at` canonicalisation and future-skew bound** for share-key
  registration (`share/mod.rs:1031-1042`): the split between handler
  canonicalisation and the driver's monotonicity check is exactly the
  M-signed_at replay fix. A regression here is not caught by the driver
  proofs, which assume the observation.
- **Conditional-write preconditions** on chunk upload/delete: `If-Match` and
  `X-Lamport-Clock` are parsed with `.parse().ok()` and default to a
  hard 400 (`chunk.rs:494-506`, `728-733`); `parse_declared_epoch` chooses
  "current epoch" when the header is absent (`chunk.rs:514`). These select
  the driver's `WriteIntent` and declared epoch.
- **ORAM path shape** (`oram.rs:376-393`): the handler, not the driver,
  decides which bucket indices are on the path and builds `create_mask`;
  `begin_oram` can only refuse a negative count.
- **Enrollment token source** (`invitation.rs:179-183`): an
  `x-enrollment-token` header silently overrides the URL token; the driver
  sees only the chosen token.
- **`X-Vela-Epoch`** (`recovery/mod.rs:637-644`) and the recovery
  `shape` facts (`operation`, `actor`, `device_authority`) are constants
  supplied by the handler, not derived by the driver.
- **Web-session poll authority** (`web_session/mod.rs:437, 475-491`): the
  constant-time secret compare and the status/expiry branching decide whether
  a capsule is released.
- **HTTPS admission** (`routes.rs:306-387`): `request_was_https`,
  `request_from_trusted_proxy` and `cf_visitor_says_https` decide whether a
  production request is refused with 426. They are pure, but unproved.
- **CORS wildcard gate** (`routes.rs:36`): `cors_origins == ["*"]` **and**
  `allow_wildcard_cors` decides whether any origin may read responses.

### 4. Reply construction carries security weight and is unproved

Every verdict-to-status table is hand-written. The proofs establish *which*
failure occurred; they do not establish the status or message. Two patterns
matter:

- **Existence oracles** are avoided by hand: pairing maps absent grant,
  absent claim and a foreign opener to the same 404
  (`rendezvous.rs:1092-1164`), `get_claim` maps "no claim" and "not yours" to
  404 (`rendezvous.rs:452-461`), and the poll handler maps missing session and
  wrong secret to the same 401 (`web_session/mod.rs:464-473`). A future edit
  to one branch re-opens the oracle without breaking any driver proof.
- **Error retention** is the reply's second input: many branches prefer the
  store/verifier error kept in `io.error` over the driver's generic failure
  (`account/delete.rs:245-253`, `auth/verify.rs:400-410`,
  `device/rendezvous.rs:1099-1152`). The proofs say the failure is honest,
  not which message is emitted.

`AppError::Internal` is scrubbed before it reaches the client
(`error.rs:62-71`), which limits leakage from the unproved branches.

### 5. Documentation inconsistency (unverified which is current)

`proof-logs/current/send-executors/README.md` ("Not covered yet") still lists
`post_send`'s recipient key read, transaction begin and quota reads, the
`GET /sends` listing, the expiry sweep and the rate limiters as uncovered.
`proof-logs/current/share-executors/README.md` ("Wave 2"), 08 lines 466-497,

### 6. What is *not* missing

- Every handler that runs a decision driver expands its crate's interpreter
  macro with `await`, and no handler calls a driver transition directly;
  `security/formal/tests/test_handler_interpreters.py` enforces both.
- Every write in the 62 non-health/non-config routes goes through an extracted
  plan; the only raw handler SQL found outside plans is the auth extractor
  (finding 2) and `GET /health`'s `SELECT 1` (row 64).
- Concurrency properties are proved at driver/composition level (pairing,
  sharing, rekey, web-session, vault upload), not at the HTTP layer.
