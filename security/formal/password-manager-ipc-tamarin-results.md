# Machine-checked model of the decide → unwrap → consume flow (Tamarin)

*Companion to `password-manager-ipc-formal-model.md`. The pen-and-paper theorems there are here re-derived symbolically in Tamarin (1.12.0, Maude 3.5.1 backend), so the secrecy claims are checked by a prover rather than by hand. Twelve theories: M1-M5, one per claim of the skeleton; M6, the real IPC handshake; M7-M8, the passkey escape and its hybrid deployment; M9a/M9b/M9c, the in-core-vs-engine-vs-in-process line; and M10, the full three-tier ladder. All produced the predicted verdict; the `.spthy` sources live alongside this document and are re-runnable. Defensive modelling only.*

> **Revision note (2026-08-06).** A review of the theories found three headline lemmas that were passing for the wrong reason, and one residual that was described as smaller than it is. All four are now fixed in the models and in this document; see [Corrections](#corrections--what-was-wrong-in-the-first-version) for what was wrong, how it was caught, and what changed. The *ordering* of the ladder and every falsification survived unchanged — the fixes tightened the top three rungs, they did not move them.

## How the threat model is encoded

The one modelling decision that carries the whole argument: **the broker's request interface is driven from the adversary-controlled channel (`In`).** In Tamarin the Dolev-Yao adversary controls `In`/`Out`, so making the broker's DECIDE step read its trigger from `In` is the faithful encoding of the **Same-Domain Capability (SDC)** assumption — a co-resident same-UID process can emit exactly the request a legitimate client emits, because the only evidence the broker checks is in-domain-forgeable. The three escapes are then encoded as the three ways to make something the broker depends on *un*-forgeable by that adversary:

- **DE (decision-escape):** release consumes a linear `Approved(item)` fact that only a human-approval rule produces and no adversary rule can fabricate.
- **SE (storage-escape):** the credential is stored `senc(cred, hk)` with `hk` held in `!Hw(...)` and never sent to `Out`, so the adversary can never derive the key.
- **TR (target-redefinition):** the broker never outputs a reusable secret; it outputs `sign(<origin, challenge>, sk)`, and a relying party accepts only a signature over its own origin and challenge.

The **consume-stage residual** (a reusable secret must reach the consuming app, which is in the domain) is modelled as `Out(cred)` on release: "plaintext enters a channel the co-resident adversary reads" is the honest symbolic stand-in for "malware reads the browser's memory after autofill."

### The M1 attack, concretely

Tamarin discharges the adversary's knowledge of `~cred` through the `Release_InDomain` case in three steps: `Setup` mints the credential → the adversary emits `In(<'request', requester>)` → `Release_InDomain` fires and `Out(cred)` hands it over → `K(cred)` holds. That is Theorem 1 as a solved constraint system: the broker cannot tell the forged request from a real one, so any usable release policy releases to the adversary.

### What the progression proves, in one line each

- **M1:** In-domain only ⇒ credential is not secret. (impossibility)
- **M2:** Put the key in hardware but leave the decision forgeable ⇒ the *key* stays secret yet the *credential* still leaks — hardware key storage alone buys nothing. (SE needs DE)
- **M3:** Add an unforgeable per-item approval ⇒ items you never use are provably secret; the item you *do* use still leaks at the consume stage. (working-set bound + consume residual)
- **M4:** Make the approval a bare unbound "yes" delivered into the domain ⇒ the adversary replays it for items you never intended. (binding, not mere unforgeability, is what matters)
- **M5:** Stop releasing a reusable secret; sign an origin-bound challenge ⇒ a signature stolen for one origin is provably useless at another; the only residual is that a resident adversary can complete a login *while present*, with nothing persisting after eviction. (TR = zero persistent, non-zero presence)
- **M6:** Put a per-client key and a bound grant on the real channel ⇒ a grant the human never issued releases nothing, a release the client never requested never happens (unless that client is compromised), a compromised browser gains only its own live grants, and a revoked or expired grant is dead. Add the desktop's replay cache and the signed request also carries *freshness*, so one captured request is worth at most one release. (handshake = M3's bound + M5's binding, with the compromise event made explicit)
- **M7:** Stop releasing the credential entirely; return a one-shot origin-bound assertion instead, signed with the item's *own* key ⇒ even the item in *active use* never reaches the adversary — the M3/M6 working-set floor is gone, not tightened. Residual, stated honestly: the adversary can consume the presence tokens the human mints while it is resident — one assertion per human action, exactly M6's one-release-per-grant — and nothing persists after eviction. What M7 buys over M6 is that the consumed thing is worth *one login at one origin* instead of a reusable credential. (TR applied to the released thing, not the gate; passkey/WebAuthn-shaped)
- **M8:** Use M7 for passkey/SSO-capable origins (the popular minority) and M6 for the legacy majority ⇒ the mode split is airtight, the passkey half leaks zero even in use, and the legacy half keeps the working-set bound — so the vault's exposure is the *legacy* working set, not the whole working set. (the practical deployment: M6 where the site demands a password, M7 where it accepts an assertion)
- **M9a:** For legacy sites, have the desktop core perform the login over its own TLS leg and hand only a session artifact to the domain ⇒ the vault password never reaches the domain at all — `credential_never_leaks` holds even for items the user logs into daily. The residual is a session — but "it dies on eviction" is a claim about the *site*, not about the design: where a live session can change the account password without re-proving the old one, the adversary converts the session into a credential it chose and keeps the account (`session_enables_persistent_takeover`, exists-trace). At sites that require step-up auth for credential change, the residual really is bounded by session lifetime (`no_takeover_at_hardened_sites`). (M7's structure applied to plain-form password sites)
- **M9b:** Do the same login *through an embedded browser engine* instead ⇒ the engine is a new domain member the same-UID adversary can watch (ptrace, `/proc`, DevTools port, X11 capture), `credential_never_leaks` **falsifies**, and the design collapses to the working-set floor — the design-review prediction, machine-checked.
- **M10:** The full ladder, one model: **M7 if the origin accepts passkey/SSO, else M9a if it is a plain-form site, else M6** ⇒ passkey and plain items leak zero even in use, and only the JS/fingerprint-bound subset leaks its working set — the composite deployment, with a machine-checked airtight three-way split.

Together these are the symbolic mirror of the master result: leakage is unavoidable in-domain (M1), storage-escape alone does not help (M2), decision-escape bounds bulk loss to the working set but not the item in use (M3), sloppy decision-escape is worthless (M4), and only target-redefinition removes persistent value (M5). M6 then shows that the *handshake* upgrades two of those: the per-client signature means a grant alone leaks nothing (M3's bound tightened), and the explicit compromise event means the residual is scoped to the compromised client — other clients' releases still require their own signed requests.

### The M6 handshake, concretely

`m6_ipc_handshake.spthy` encodes the VELA browser↔desktop channel as four phases and then asks Tamarin for secrecy and injective agreement on the whole thing:

- **Channel setup** — the desktop writes a per-session capability to `ipc_auth.json`; modelled as `Out(~cap)` because a same-UID process can read that file (SDC, restated for the real channel). The honest native-messaging host is a transparent relay and is subsumed by the adversary.
- **First-use pairing** — the joining client generates its own keypair and displays `h(pk)` on its own screen (`Client_Join`); the human reads that phrase out of band and confirms (`Human_Confirm_Pairing`); the desktop enrolls the key only after that confirmation (`Desktop_Enroll`). `enrollment_agrees_with_human_confirmation` verifies that enrollment ⟸ displayed-fingerprint-the-human-confirmed: no adversary rule can produce the confirmation, so there is no way to enroll a key the human never saw.
- **Per-client key exchange** — every fill request is signed by the client's private half and verified against the enrolled public key (`Client_Request`, `Desktop_Release`).
- **Grant lifecycle** — issue (`Human_Approve`, bound to exactly one (client, origin, item)), use (`Desktop_Release`, consuming the grant *and* the signed request), anomaly-reconfirm (grants are single-use and bound to the triple, so any use outside it needs a fresh human issue), expire and revoke (`Grant_Expire`, `Grant_Revoke`).

The verdicts land as predicted. Three worth reading closely:

- `release_requires_client_request` (verified, all-traces) is the **agreement** result: every release is backed by a human-issued grant *for that exact (client, origin, item)* and by the client's own signed request *carrying the same nonce the release consumed* — or, in the only escape, that client having been compromised. Injectivity is proved separately from both sides: `grant_is_single_use` (one release per grant) and `request_is_single_use` (one release per request). The second of those depends on the desktop's replay cache, modelled as the `RequestNonceIsFresh` restriction; without it the agreement is genuinely non-injective, and one captured request backs several releases (see [Corrections](#corrections--what-was-wrong-in-the-first-version)).
- `compromised_client_cannot_act_as_others` (verified, all-traces) is the **compromised-browser bound**: if only browser C2 is compromised, a release for a different client C can only ever happen through C's own signed request — the compromise buys the attacker nothing outside C2's own grants. `compromised_browser_residual` (exists-trace) shows the honest bound: a compromised C *can* still complete a fill while a grant for (C, ·, ·) is live and fresh — the same presence residual as M5, now with the key the browser already holds.
- `unused_item_secret` (verified, all-traces) is the **bulk bound surviving full compromise**: an item never released never reaches the adversary, even if every client key is leaked. The consume-stage residual (`used_item_leaks`, exists-trace) still holds — the item in active use reaches the domain.

### Where the handshake sits relative to the five skeleton models

M1–M5 deliberately stripped the channel to isolate the decide/unwrap/consume skeleton; M6 is that skeleton *with the real channel put back*. It does not overturn the earlier verdicts — it refines two of them. Where M3 proved "items never approved stay secret," M6 proves the same claim with the approval now a bound grant and adds that even an approved-but-never-used item stays secret (`unused_item_secret`); where M5 proved cross-origin safety of a signature, M6 proves the release itself is origin- and item-bound (`no_cross_origin_release`). And it adds what no skeleton model could express: a *compromise event*, so "what does a pwned browser actually get?" has a machine-checked answer.

### M7 and M8 — past the working-set floor

M3/M6 share one ceiling: the working set, because *using* an item means its plaintext reaches the domain. M7 attacks the premise, not the mechanism: the broker stops releasing a reusable secret and answers a fresh challenge with a one-shot origin-bound assertion.

The item stored for a passkey origin **is** the credential's private key (WebAuthn: one credential = one keypair, scoped to one origin), the assertion is `sign(<O, chal>, cred)` signed with that key, and `pk(cred)` is registered at the relying party and public. So `credential_never_leaks` is a real symbolic secrecy result about a term the adversary watches being *used*: it sees the public half and an unbounded number of signatures under the private half, and still cannot derive it. (A mutation that adds a single `Out(cred)` rule falsifies it in 3 steps — the lemma has teeth.) `assertion_one_shot` makes a stolen assertion worthless: one accept per fresh challenge, and the challenge is consumed.

Serving an assertion consumes a **user-presence token** minted by a deliberate human action — WebAuthn's UP/UV, and the passkey tier's analogue of M6's `Human_Approve`. `assertion_requires_user_presence` verifies there is no assertion without one, and `assertions_bounded_by_presence` verifies the binding is injective: *n* logins cost the adversary *n* human actions. Without that gate the assertion path is a free oracle, and the residual is not "one assertion while present" but standing authentication as the user at every passkey origin — which is what the first version of this theory accidentally modelled. Together with `credential_never_leaks`, the gate is also the statement that a fully compromised browser cannot mint assertions: it never holds the key, and it cannot manufacture presence.

That is the working-set floor gone, at the cost of requiring the site to accept assertion/SSO auth.

M8 is the deployment that accepts that cost is only partial: the vault tags every item with its origin's auth mode at minting time, the passkey-capable origins take the M7 path and the legacy majority takes the M6 path, and each path is gated on the mode. `released_items_are_legacy` and `asserted_items_are_passkey` verify the split is airtight — a passkey item cannot be drained via a credential release, and a legacy item cannot be served an assertion. `passkey_item_never_leaks` plus `legacy_unused_item_secret` are the hybrid's bound: the vault's exposure is the *legacy* working set, and the M6 agreement/compromise lemmas carry over unchanged for that half. Quantitatively (see the graph), with the popular quarter of sites on the passkey path, the 2-month leak drops from ~71 (M6) to ~32 (M8) — the passkey half contributes zero.

### M9a, M9b and M9c — in-core vs. engine vs. in-process interpreter

M8's legacy half still releases passwords, so it keeps the working-set floor. M9 attacks that floor for *plain-form* legacy sites by moving the login out of the browser: the desktop core submits the credential to the site over its own TLS leg, and only a session artifact reaches the domain (`m9a_in_core_login.spthy`). `credential_never_leaks` and `used_item_still_secret` verify that **K(cred) never holds — even for an item the site has accepted a login for**. That is M7's structure applied where the site only speaks passwords.

**What the session is worth is a site property, and the model now says so.** `session_expiry_is_effective` verifies only the narrow claim that a *dead* session cannot be used. The broader claim — "nothing persists after eviction" — is false at any site where a live session can change the account password or e-mail without re-proving the old one, which is most of them. The theory models that explicitly as `Site_Session_Escalate`, gated on a per-site mode: at a `'selfserve'` site, `session_enables_persistent_takeover` (exists-trace) verifies that the adversary rotates the credential to a value **it** chose and keeps the account after the session is gone; at a `'hardened'` site, `no_takeover_at_hardened_sites` (all-traces) verifies the residual really is bounded by session lifetime. The vault credential never leaks in either mode — the tier's secrecy claim is untouched — but the *persistence* claim needs the site to require step-up auth for credential change. For a deployment that means the plain tier is only as good as its worst site, and picking that tier should check the site's reset policy, not just its login form.

The critical design line is drawn by M9b (`m9b_engine_login.spthy`), which encodes doing the same login *through an embedded browser engine* instead. The engine is a domain member: the credential is handed to it over an observable channel (`Out(cred)`), so `credential_never_leaks` **falsifies** and `credential_leaks_via_engine` (exists-trace) confirms the leak is real — a same-UID adversary that can watch the engine (ptrace, `/proc/PID/mem`, the DevTools debugging port, X11 capture) gets every password the engine touches. M9b is the working-set floor with extra attack surface: the moment a legacy site needs JS, a CAPTCHA, or browser-fingerprint-bound sessions, it forces the engine, and the engine collapses M9 back to M6-grade. The honest deployment is therefore *three* tiers: passkey origins → M7 (zero), plain-form legacy origins → M9a in-core (zero), JS/fingerprint-bound legacy origins → M6 (working set of that subset only).


**M9c** (`m9c_inprocess_sandbox.spthy`) answers the question M9b keeps prompting and does not settle: *couldn't we run a small JS runtime inside the core, where nothing can watch it?* M9b's falsification turns on a single step — the credential crosses to a separate process over an observable channel — and an in-process interpreter (QuickJS as a library, or a JS engine compiled to WASM under an in-process sandbox) is not that object. The proof does not transfer, so the design deserves its own theory rather than an argument by analogy.

It wins the thing it claims. `credential_never_leaks_without_escape` **verifies**: with no channel there is nothing to attach a debugger to, and absent an escape no credential reaches the domain. M9b cannot state that lemma at all. Removing the `Out(cred)` step is exactly what earns it — putting it back falsifies the lemma and reproduces M9b.

What it costs is a currency M9b never had to name. To log in to a JavaScript site you must run the site's JavaScript, which is code the adversary chose; and the interpreter now shares an address space with the vault and the key that unseals it. `unused_credentials_stay_secret` is the lemma that separates the two designs, and it was checked in both rather than asserted: **verified in M9b, falsified in M9c**. In the engine design an escape yields what the engine held — the item in flight, bounded by the working set, which is the M6 floor the ladder already lives with. In the in-process design it yields the store: items never logged into, sites the user has not visited in years, and `escape_takes_the_master_key` confirms the key as well. The same top-level verdict for opposite reasons, and the blast radius is the comparison that matters.

The obvious repair closes the loop. Putting the interpreter back in its own process to contain an escape reintroduces the observable channel — that is M9b, by construction. *The isolation that makes the runtime safe is the same isolation that makes it a domain member.* Neither theory proves that on its own; it is what the two say side by side.

Feasibility is a separate objection and independently fatal: a login on a fingerprinting site needs canvas, WebGL and an audio stack, so anything that satisfies those checks is a renderer, and a renderer is an engine. M9c is therefore not a tier — it is the machine-checked reason there is no fourth tier, and JS/fingerprint-bound sites stay on M6.
### M10 — the full ladder, as one model

That three-tier deployment is `m10_full_ladder.spthy`: a single theory whose vault tags every item with its origin's tier (`'passkey'` / `'plain'` / `'js'`) and whose three serving paths are each gated on the tag. The airtightness lemmas of M8 extend to three modes — `released_items_are_js`, `asserted_items_are_passkey`, `authed_items_are_plain` — so a passkey item can no more be drained via a credential release than a plain item can be served an assertion or a js item routed through the in-core leg. The tier guarantees all carry over unchanged: `passkey_item_never_leaks` and `plain_item_never_leaks` (zero, even in use), `js_unused_item_secret` (working-set bound), plus the M6 agreement/compromise, M7 origin-bound/one-shot, and M9a session-expiry lemmas. The exists-trace set confirms all three tiers are live and the only item that reaches the adversary is a used js item.

Quantitatively this is the endpoint of the whole progression: on the graph, the 2-month leak falls from **200** (M1/M2/M4/current-no-biometric) → **71** (M3/M6 working set) → **32** (M8, passkey half removed) → **12** (M10, plain-form half removed too), with M7/M9a/M5 at zero. The residual that remains — a handful of JS-bound legacy items — is the irreducible floor for the sites that will not accept an assertion, cannot be logged into in-core, and demand a literal password in the page.

The graph is unchanged by the corrections below: it counts *credentials that reach the adversary*, and none of the three fixes moves an item from one side of that line to the other. What the fixes change is the cost and the shape of the residual at the top two tiers — the passkey tier's assertions now cost one human action each rather than being free, and the plain tier's session residual is bounded by session lifetime only at sites that harden credential change. Both are things the leak curve never measured.

## Caveats — what this does and does not certify

- **Symbolic (Dolev-Yao) model, perfect cryptography.** Signatures are unforgeable and `senc` is ideal by assumption. Real-world breaks — weak RNG, side channels, a memory-scraping technique that reaches the key *inside* the hardware boundary — are outside symbolic scope. The models certify the *logic* of the trust-domain argument, not the cryptography or the hardware.
- **SDC is an encoded assumption, and it is the point.** M1 falsifies *because* the request arrives via `In`. If a real deployment could make the request channel genuinely un-forgeable, M1 would not falsify — but by Theorem 2 that is precisely one of the escapes (DE), so the framework is consistent: the only way to stop M1's attack is to add an escape, which is what M3/M5 do. M6 encodes the same assumption for the real channel: the capability token is adversary-visible by construction, and the human pairing-confirmation is the *only* out-of-band step — which is exactly why it is modelled as an honest rule no adversary can forge.
- **M6 models the handshake's logic, with two deliberate idealisations.** The out-of-band pairing step (`Human_Confirm_Pairing`) is an honest rule, not a cryptographic mechanism — it encodes "the human physically compares the fingerprint phrase on the joining device's own screen." The compromise event (`Corrupt_Client`) is an explicit rule, not a side-channel analysis: it says "the browser's private key leaks," it does not explain how. Both are the right level for a trust-domain argument, and both are stated in the model's comments.
- **M7/M8 carry two further idealisations.** M7 models a passkey ceremony as a signature over `<origin, challenge>` under the credential's own key, plus a consumable user-presence token — it abstracts the rest of the real WebAuthn envelope (attestation, clientDataJSON, signature counter) exactly as M5 abstracted origin-signing. The presence token is an honest rule, on the same footing as `Human_Confirm_Pairing`: it encodes "the human deliberately authorised this one assertion," it does not model the authenticator UI that makes that unforgeable. M8's mode tag (`'passkey'`/`'legacy'` per item) is a *deployment* input, not something the protocol can learn by itself: the model assumes the split is assigned at minting time and kept honest, and the airtightness lemmas prove only that *given* that tag, the two paths cannot cross. A real deployment must decide which origins are passkey-capable (and the passkey path only helps for origins that actually accept assertion auth — the legacy majority is exactly why M6 stays).
- **M9a's private leg is the claim, M9b is one boundary, and the site's reset policy is the other.** In M9a the desktop→site leg is a private fact (`CredToSite`), encoding the desktop's own TLS connection inside the trusted core. The model proves the *structure* — no credential ever transits a domain-observable channel — and carries the standard out-of-scope caveat for anything that reaches inside the trusted core (memory scraping, TLS-stack compromise). M9b draws the implementation boundary: swap the private leg for an embedded engine and the same theory falsifies `credential_never_leaks`, the machine-checked form of "don't implement this with Selenium." The `'hardened'`/`'selfserve'` site mode draws the other one: the tier's secrecy claim holds regardless, but its *persistence* claim is only as strong as the site's policy on changing credentials from a live session, and that mode is a deployment input the model does not verify.
- **These are argument-isolating models, not a full protocol.** They deliberately strip away channel establishment and framing to isolate the decide/unwrap/consume skeleton. They are evidence for the *impossibility and the escape structure*, not a certificate for a shippable VELA wire protocol. M6 restores pairing, per-client keys, the grant lifecycle, and (as of this revision) the request replay cache, but it still abstracts framing, endpoints and the OS peer-identity check behind honest rules and restrictions — it certifies the handshake's *logic*, not its bytes. In particular `RequestNonceIsFresh` is a restriction, i.e. an assumed-correct replay cache, not a model of the bounded-memory cache a real implementation would ship.
- **Tamarin answers "which items can leak," not "how many."** The qualitative boundary (unused secret vs. used leaks, cross-origin safe vs. present-session drivable) is what is machine-checked here. The *quantitative* magnitude is turned into the log-time graph by `password-manager-ipc-leak-graph.py` (200-item vault, 2 months, Zipf item popularity, stated attacker rates): full-vault solutions hit 200, M3/M6 plateau at the working set, M8 at the *legacy* working set, M5/M7 at zero. Symbolic for the boundary, stochastic for the magnitude.

## Natural next step

That next step — encode the real IPC handshake and prove secrecy + injective agreement on it, compromised-browser case included — is now **done, as M6** (`m6_ipc_handshake.spthy`): native-messaging channel setup, first-use pairing with a human-verifiable fingerprint phrase, per-client key exchange, the request replay cache, and the Approved-grant lifecycle (issue / use / anomaly-reconfirm / expire / revoke) are all in the theory, and the secrecy, agreement and both injectivity lemmas, including the compromised-browser bound, verify without an oracle.

The follow-up ladder is also built and verified: **M7** (`m7_oneshot_assertion.spthy`) shows the passkey-shaped escape from the working-set floor (credential never leaks, even in use, with the assertion path gated on user presence); **M8** (`m8_hybrid.spthy`) is the deployment of M7-for-passkey-origins + M6-for-legacy with a machine-checked airtight mode split; **M9a/M9b** (`m9a_in_core_login.spthy`, `m9b_engine_login.spthy`) draw the in-core-vs-engine line (M9a reaches M7-grade secrecy for plain-form sites only if the login stays in the trusted core; M9b falsifies `credential_never_leaks` — the model's answer to "couldn't another app grab it from the Selenium?"); and **M10** (`m10_full_ladder.spthy`) is the final composite — **M7 if not M9a if not M6** — with the three tiers machine-checked airtight and each tier's guarantees intact. The log-time graph (`password-manager-ipc-leak-graph.png`) quantifies all twelve curves.

What the models still leave open, in descending order of value:

1. **A wire-protocol certificate.** All eleven models abstract framing and the OS peer-identity check (`SO_PEERCRED`/`LOCAL_PEERCRED`/named-pipe DACL) behind honest rules, and the replay cache behind a restriction. Encoding those as explicit messages and state — and proving the framing does not create a path the abstract model missed — is the step from "the logic holds" to "this wire format holds."
2. **The real WebAuthn ceremony in M7/M8.** The passkey path is a signature over `<origin, challenge>` under a per-origin credential key, gated on an abstract presence token; a full model of the CTAP2/WebAuthn envelope (clientDataJSON, the signature counter, the attestation round, and UV as a mechanism rather than an honest rule) would close the gap between the abstract assertion and what `webauthn.rs` actually emits and the RP verifies.
3. **The in-core login leg in M9a.** `CredToSite` is a private fact encoding the desktop's own TLS connection; the model certifies the *structure* (password never in the domain), not the TLS stack. Memory-scraping that reaches inside the trusted core is the same out-of-symbolic-scope residual as hardware-key scraping. M9b is the machine-checked warning for the obvious implementation shortcut.
4. **The human-action assumptions, and a measurement that they fail.** `Human_Confirm_Pairing` and M7's `Human_User_Presence` are honest rules: no adversary rule produces them, so in the model a co-resident process cannot forge a human. That is the assumption the whole presence bound rests on, and it was measured on a real machine during the M7 implementation — it does not hold there.

   On an Arch/Hyprland desktop the user was in the `input` and `uinput` groups and `/dev/uinput` was group-writable, so an unprivileged same-UID process could create a virtual keyboard (confirmed: device created, no keystrokes sent). Wayland blocks compositor-level injection such as `XTEST`, but `/dev/uinput` sits *below* the compositor and presents as real hardware. A confirmation dialog is therefore clickable by the adversary the model assumes cannot click it, on any machine with that group membership — routine for ydotool, gaming peripherals and remote-desktop tools.

   What survives is the biometric factor: no synthetic input satisfies a fingerprint reader. So `assertion_requires_user_presence` should be read as holding **only where a real verification factor exists**; where the deployment falls back to a dialog, the lemma is true of the model and false of the machine. An on-screen decoy-pick (enrollment v3) has the same exposure. This is the clearest case in the whole document of a symbolic assumption that a deployment has to earn rather than inherit.
5. **Which origins are passkey-capable.** M8's mode tag is an input; a real deployment needs a trustworthy, current decision procedure (and a fallback path for origins that silently drop WebAuthn) — a protocol-design problem, not a symbolic one.
6. **Which sites harden credential change.** M9a/M10's `'hardened'`/`'selfserve'` mode is the same kind of input, and there is no reliable way to discover it automatically. Until there is, the plain tier's "nothing persists" claim should be stated as conditional in any user-facing material.
7. **Pairing proves a confirmation happened, not that it was the right one.** `enrollment_agrees_with_human_confirmation` verifies that no key is enrolled without a human confirming a fingerprint the joining device displayed. It does *not* model a human who confirms the wrong fingerprint — `Human_Confirm_Pairing` has no way to refuse, so a fooled human is outside the model. That is the same class of assumption as item 4, and it is the one an attacker would actually attack.

## Corrections — what was wrong in the first version

Four defects were found by re-deriving the results rather than re-reading them, and all four are fixed above. Recording them because three of the four were lemmas that *passed*, which is the failure mode formal models are worst at surfacing.

| # | Defect | How it was caught | Fix |
|---|---|---|---|
| 1 | **M7's `credential_never_leaks` was a tautology.** The vault item was an unused premise of `Sign_Assertion`, and the assertion was signed with an unrelated device key. Tamarin was confirming "no rule writes `Out(cred)`" — checkable by grep. | Deleted the entire vault from the theory; every lemma still verified, `credential_never_leaks` in 2 steps. | The vault item **is** the credential's private key; the assertion is signed with it and `pk(cred)` is published. A mutation adding one `Out(cred)` rule now falsifies in 3 steps. Same fix in M8/M10. |
| 2 | **M7's residual was understated.** `Sign_Assertion` fired straight off `In(...)` with no human in the loop, making the assertion path a free oracle. "A resident adversary can drive one assertion while present" was wrong: it could drive unbounded logins at every passkey origin. | Added an exists-trace for three distinct accepts — verified in 16 steps. | A user-presence token (WebAuthn UP/UV) is minted by a human action and consumed per assertion, with `assertion_requires_user_presence` and `assertions_bounded_by_presence` verifying the gate. The residual is now genuinely one assertion per human action. Same fix in M8/M10. |
| 3 | **M6's "injective agreement" was not injective.** `Desktop_Release` never checked the request nonce for freshness, so one captured client-signed request could back several releases — the per-client signature was carrying authenticity but no freshness. | Instrumented `Released` with the nonce and asked whether a request is single-use: falsified in 13 steps, *without* any client compromise. (The matching-nonce direction did verify, so the agreement half was sound.) | Added the desktop's replay cache as the `RequestNonceIsFresh` restriction and split the claim into `release_requires_client_request` (agreement, same nonce) and `request_is_single_use` (injectivity). Same fix in M8/M10. Real-world impact was bounded — the single-use *grant* was doing the injective work — but the label was wrong. |
| 4 | **M9a modelled the session's existence but not its power.** "The only residual is a session that dies on eviction" is false wherever a live session can change the account password without re-proving the old one. | Not a prover result — a gap in what was modelled at all. | `Site_Session_Escalate` gated on a per-site `'hardened'`/`'selfserve'` mode, with `session_enables_persistent_takeover` (exists-trace) and `no_takeover_at_hardened_sites` (all-traces). The tier's secrecy claim is untouched; its persistence claim is now conditional and says on what. |

Three smaller things went with them: M7/M8's `RP_Accept` accepted a signature under *any* registered device key rather than the one registered for its own origin (now `!RpKey(O, pkey)`); `device_key_secret` was dropped as a separate lemma, since with the credential as its own signing key `passkey_item_never_leaks` states it directly; and the abstract's "six small theories" was five models out of date.

What did **not** change: every falsification (M1, M2, M4, M9b), the ordering of the ladder, and the leak graph. The corrections tightened the top three rungs and made two residuals honest; they did not move any item from one side of the leak boundary to the other.
